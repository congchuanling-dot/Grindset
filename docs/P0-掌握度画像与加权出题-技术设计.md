## 2. 总体流程

### 2.1 答题收束后沉淀

```
POST /api/interviews/{id}/answers
  → LLM 返回点评 + evaluation(knowledgePoints, score)
  → 事务 A:写 ANSWER/FEEDBACK、题目 status=3、completed_questions+1
  → 事务 A 提交
  → 事务 B(best-effort):KnowledgeProfileService.record(userId, sessionId, points, score)
        → 逐个知识点:归一 → 查/建 knowledge_points
        → SELECT user_knowledge_states ... FOR UPDATE
        → 存在则 EMA 更新,不存在则插入
  → 返回 AnswerResult
```

**事务 B 失败不回滚事务 A**:答题记录优先,画像允许最终一致。失败只记 error 日志,由画像重建兜底。

### 2.2 出下一题前取候选

```
POST /api/interviews/{id}/questions
  → 读取本场已收束题目的知识点(covered)
  → KnowledgeProfileService.weightedCandidates(userId, covered, 5)
        → 查该用户全部 state
        → 排除 covered
        → 计算权重 → 加权随机抽 5 个
  → 候选连同简历、岗位、已考察知识点一起拼进主问题 prompt
  → SSE 出题
```

候选为空(新用户/知识点全被本场覆盖)时,prompt 不出现该段,行为与当前版本完全一致。

### 3.3 设计取舍

- **知识点单独成表**:名称需要跨用户复用,后续题库、错题本、人工合并都挂在 `kp_id` 上;直接把名称存在 state 表会导致无法合并、无法统计。
- **不建知识点树**:本 P0 只做平铺名称 + 领域,树形结构等题库模块再引入。
- **prev_mastery 冗余**:画像页趋势只需一次比较,避免再存历史流水;完整历史后续按需加 `knowledge_state_logs`。
- **不改 interview_questions**:题目行仍保存 `knowledge_points` 原始 JSON,作为重建和审计的源数据。
- **JSON 列不新增**:画像全是强结构字段,用普通列即可。

## 4. 算法

### 4.1 名称归一

```java
static String normalize(String raw) {
    String text = Normalizer.normalize(raw, Normalizer.Form.NFKC)
            .trim()
            .toLowerCase(Locale.ROOT);
    text = text.replaceAll("[\\s\\p{Punct}，。、；：（）【】《》“”‘’·—…]", "");
    return text.length() > 128 ? text.substring(0, 128) : text;
}
```

- 归一后为空或长度 < 2 的知识点丢弃,避免"啊""这个"之类噪声。
- `name` 保留模型原始输出的首个写法,后续复用。
- 别名合并(如"RDB与AOF"与"Redis持久化")不在 P0 做,列入后续人工合并。

### 4.2 领域推断

用关键词映射,未命中归"其他":

| 关键词 | 领域 |
|---|---|
| redis | Redis |
| mysql / innodb / 索引 / 事务 | MySQL |
| jvm / gc / 垃圾回收 / 类加载 | JVM |
| java / 线程 / 并发 / spring | Java |
| tcp / http / 网络 / 握手 | 网络 |
| 操作系统 / 进程 / 内存 / 页表 | 操作系统 |
| 算法 / 数据结构 / 复杂度 | 算法 |
| llm / transformer / 大模型 / rag | AI |
| 项目 / 架构 / 系统设计 | 项目 |

先匹配更具体的关键词(Redis/MySQL/JVM),再匹配泛化的 Java/项目,避免"Redis 持久化"被归到 Java。

### 4.3 掌握度 EMA

```java
int observation = (score - 1) * 25;            // 1→0, 2→25, 3→50, 4→75, 5→100
int next = existing
        ? (int) Math.round(oldMastery * 0.7 + observation * 0.3)
        : observation;
```

更新字段:

```
prev_mastery      = 旧 mastery
mastery           = next
practice_count    = 旧值 + 1
correct_count     = 旧值 + (score >= 3 ? 1 : 0)
last_score        = score
last_session_id   = sessionId
last_practiced_at = now
```

### 4.4 权重与抽样

```java
double weight(UserKnowledgeState s, LocalDateTime now) {
    double level = s.getMastery() < 40 ? 3.0 : s.getMastery() < 75 ? 1.8 : 1.0;
    double wrong = s.getLastScore() != null && s.getLastScore() <= 2 ? 1.5 : 0.0;
    double days = s.getLastPracticedAt() == null ? 30
            : Duration.between(s.getLastPracticedAt(), now).toDays();
    double stale = Math.min(Math.max(days, 0), 30) / 30.0;
    return level + wrong + stale;
}
```

抽样:

1. 过滤本场 `covered` 中的知识点。
2. 计算总权重 `total`。
3. 循环 `limit` 次:`r = random(0, total)`,累加权重命中一个,移除后重算 `total`。
4. 返回 `List<Candidate(name, levelLabel)>`,按抽中顺序。

`limit = 5`。随机源用 `ThreadLocalRandom.current()`;测试用可注入的 `Random` 重载,避免概率断言不稳定。

### 4.5 等级与趋势

```
WEAK       mastery < 40
LEARNING   40 <= mastery < 75
MASTERED   mastery >= 75

trend: prev_mastery == null → NEW
       mastery > prev      → UP
       mastery < prev      → DOWN
       else                → FLAT
```

## 5. 后端实现

### 5.1 KnowledgeProfileService

```java
@Service
public class KnowledgeProfileService {

    /** 答题收束后沉淀;独立事务,best-effort */
    public void record(long userId, long sessionId, List<String> points, int score);

    /** 出题候选:排除本场已考察,按权重随机抽 limit 个 */
    public List<Candidate> weightedCandidates(long userId, List<String> covered, int limit);

    /** 评分 prompt 复用:取用户最近/最薄弱的 N 个知识点名称 */
    public List<String> knownNames(long userId, int limit);

    /** 画像页查询 */
    public KnowledgeProfileView profile(long userId, String level, String domain, int limit);

    /** 管理员按用户重建 */
    public RebuildResult rebuild(long userId);

    public record Candidate(String name, String level) {}
    public record RebuildResult(int questions, int states) {}
}
```

`record` 内部:

```java
if (points == null || points.isEmpty() || score < 1 || score > 5) {
    return;
}
transactionTemplate.executeWithoutResult(status -> {
    for (String raw : points) {
        String normalized = normalize(raw);
        if (normalized.length() < 2) continue;
        KnowledgePoint kp = findOrCreate(raw, normalized);
        UserKnowledgeState state = stateMapper.selectForUpdate(userId, kp.getId());
        if (state == null) {
            insertState(...);
        } else {
            updateStateByEma(...);
        }
    }
});
```

`findOrCreate`:
1. `selectOne(normalized_name = ?)`。
2. 不存在则插入;捕获 `DuplicateKeyException` 后重新查询(并发兜底)。

`selectForUpdate` 放在 Mapper:

```java
@Select("SELECT * FROM user_knowledge_states WHERE user_id = #{userId} AND kp_id = #{kpId} FOR UPDATE")
UserKnowledgeState selectForUpdate(@Param("userId") long userId, @Param("kpId") long kpId);
```

### 5.2 答题链路改造

位置:[InterviewService.answer](../backend/src/main/java/com/grindset/backend/service/InterviewService.java#L257-L356)

```java
// 现有事务 A 保持不变
transactionTemplate.executeWithoutResult(status -> { ... });

// 事务 A 提交后再沉淀画像
try {
    knowledgeProfileService.record(userId, id,
            finalEvaluation.getKnowledgePoints(), finalEvaluation.getScore());
} catch (Exception e) {
    log.error("掌握度画像更新失败 userId={} sessionId={}", userId, id, e);
}
```

要点:

- 不把画像写入塞进事务 A,避免画像异常导致"答案丢失"。
- 题目收束只能发生一次,重复提交会被 `latestQuestion.status != 2` 拦截,画像不会重复累加。
- 若进程在事务 A 提交后崩溃,画像会缺一条;由重建接口修复,属于可接受的最终一致。

### 5.6 画像重建

新增 `AdminKnowledgeController`:

```
POST /api/admin/knowledge/rebuild?userId=1830...
Header: X-Admin-Token
```

流程:

1. 校验管理员令牌(复用 [AdminGuard](../backend/src/main/java/com/grindset/backend/common/AdminGuard.java))。
2. 按 `sessions.created_at ASC, questions.seq ASC` 取该用户全部 `status=3 且 score 非空` 的题目。
3. 删除该用户全部 `user_knowledge_states`。
4. 按顺序重放 `record` 的纯计算逻辑,重建 state。
5. 返回题目数与 state 数。

注意:

- 不删除 `knowledge_points`,避免影响其他用户。
- 重建期间该用户可能正在答题,单实例下用 `ConcurrentHashMap<Long, ReentrantLock>` 按 userId 串行化;多实例后续改 Redis 锁。
- 重建是管理操作,不在前端暴露。

### 5.7 并发与一致性

| 场景 | 处理 |
|---|---|
| 同一用户两场面试同时答题 | `user_knowledge_states` 的 `UNIQUE(user_id, kp_id)` + `SELECT ... FOR UPDATE` 串行化同一行 |
| 两个请求同时创建同一知识点 | 唯一键兜底,捕获 `DuplicateKeyException` 后重查 |
| 同一题重复提交 | 现有会话锁 + 题目状态判断,只有第一次收束生效 |
| 画像更新失败 | 不回滚答题;记日志;重建修复 |
| 重建与答题并发 | 用户级内存锁;多实例后续升级 |

### 5.8 降级

- 画像为空:候选为空,出题 prompt 不带候选段,行为与当前版本一致。
- 画像查询超时/异常:捕获后按空候选处理,不影响出题。
- 画像页接口异常:前端展示错误态和重试,不影响面试主流程。
- 前端画像卡片失败:静默隐藏,不阻塞创建面试。

## 8. 测试

### 8.1 单元测试

| 用例 | 断言 |
|---|---|
| `normalize("Redis 持久化。")` | 等于 `normalize("redis持久化")` |
| 空串/单字符 | 被过滤,不建知识点 |
| EMA 首次 3 分 | mastery=50 |
| EMA 80 分后答 1 分 | mastery=56 |
| 权重:掌握度 35 + 最近 2 分 + 10 天 | 明显高于掌握度 85 + 最近 5 分 + 1 天 |
| 抽样排除 covered | 结果不含本场已考察知识点 |
| 候选不足 5 个 | 返回全部可用,不报错 |

权重随机性测试使用可注入 `Random` 的重载,断言集合和权重排序,不断言具体概率。

### 8.2 持久化测试

沿用 [AuthPersistenceTest](../backend/src/test/java/com/grindset/backend/AuthPersistenceTest.java) 的 `@SpringBootTest` 真库风格:

| 用例 | 步骤 |
|---|---|
| 首次沉淀 | 调 `record` → 查 `user_knowledge_states`,字段符合预期 |
| 再次沉淀 | 调两次 → `practice_count=2`,mastery 按 EMA |
| 知识点归一 | `"Redis 持久化"` 与 `"redis持久化"` 落到同一个 `kp_id` |
| 多知识点 | 一次传 3 个 → 生成 3 条 state |
| 重建 | 造 2 场已收束题目 → `rebuild` → state 与重放结果一致 |

### 8.3 回归测试

- 画像为空时,`nextQuestion` 的 prompt 不含"参考薄弱知识点"段。
- 画像服务抛异常时,`answer` 仍返回成功。
- 删除面试记录后,画像数据仍存在。
- 前端画像接口 401 时,面试入口不崩溃。

### 8.4 手工验收

1. 新账号完成一场 3 题面试,记录每题知识点与分数。
2. 打开画像页,核对掌握度、练习次数、最近得分。
3. 再开一场,观察题目是否围绕薄弱点;在日志中确认 prompt 带候选。
4. 再答一题,确认掌握度按 EMA 变化。
5. 触发重建,确认数据一致。

## 10. 已知限制与后续

| 项 | 现状 | 后续 |
|---|---|---|
| 知识点命名 | 归一 + prompt 复用,仍有碎片 | 人工合并 / 别名表 / 向量相似度 |
| 领域 | 关键词映射,较粗 | LLM 输出领域或建知识点树 |
| 岗位相关性 | 全部知识点参与候选,LLM 自行忽略 | 加"知识点 × 岗位"亲和度 |
| 复习排期 | 只有遗忘加成,没有 SM-2 | P1 引入下次复习时间 |
| 画像历史 | 只存最新值,趋势仅一层 | 增加 `knowledge_state_logs` 流水 |
| 一致性 | best-effort,可能缺一条 | 事件表 + 定时补偿 |
| 多实例 | 用户级内存锁 | Redis 分布式锁 |
| 可视化 | 列表 + 进度条 | 雷达图 / 热力图 |
| 参考答案 | 不生成 | 归入错题本/复盘模块 |
