# AI 面试复习闭环系统 · 产品需求文档(PRD)

> 版本:v0.1(草稿,待评审)
> 作者:从传领
> 日期:2026-11-14
> 一句话定位:一个**针对后端/AI 岗八股的个性化面试复习系统**,通过"AI 出题 → 答题 → 评分定位知识点 → 更新掌握度画像 → 按薄弱点加权再出题"的闭环,让用户越练越准。

---

## 0. 文档约定

- 本 PRD 只定义 **v1(裸闭环 MVP)** 必做范围,其余功能标注为 P1/P2,防止范围膨胀导致烂尾。
- 优先级:**P0 = MVP 必做;P1 = 闭环跑通后做;P2 = 远期/可选**。
- 本项目有**双重目标**:① 真有人用(秋招"真实用户"亮点);② 展示后端 + AI 工程能力(秋招简历亮点)。两者冲突时,**先保 ①(能用),再加 ②(工程装甲)**。

---

## 1. 背景与问题

### 1.1 用户痛点
- 八股复习靠死题库,**题目和用户水平脱节**:会的反复看,不会的没人盯。
- 复习后**没有反馈**:答完不知道哪个知识点真的懂了,第二天就忘。
- 现有工具多为**静态题库**,缺少"针对你个人弱点"的动态调度。

### 1.2 机会
- LLM 让"出题/评分/追问/知识点定位"从不可能变为白菜功能。
- **壁垒不在"出题",在"反馈线"**:系统记住你哪个知识点答崩了,下一轮专挑弱点追问,直到会为止。这是本产品的灵魂与差异点。

### 1.3 非目标(明确不做)
- ❌ 音频语气分析("额、啊"检测)——难且无价值,砍。
- ❌ AI 爬全网题**作为线上主力题源**——质量/版权不可控。线上出题以"按知识点现场生成 + RAG 喂权威资料"为主;**爬题仅作冷启动种子/测试数据**(面试话术:RAG 现场生成为主,爬题仅作测试种子)。
- ⚠️ 真实支付:**两档可插拔**(见 §7)。默认人工兑换码;进阶用支付宝**沙箱**跑通全自动回调对账。个人真实收款作为远期可选,不作为必做(个人无商户号无法编程对账)。
- ❌ 数据库/Redis 集群——真实并发撑不起,单机即可;集群是"量级到了才上"。
- ❌ SpringCloud/微服务——秋招后端少考,单体 SpringBoot 把并发/容错/计费做扎实,深度 > 广度。

## 2. 目标与成功指标

### 2.1 产品目标
| 阶段 | 目标 |
|---|---|
| MVP | 自己用 3 天,确信"它在针对我的弱点" |
| v1 上线 | ≥ 20 个与作者无关的陌生用户,且有二次使用 |
| 工程 | 单机压测模拟 3000 并发不雪崩,成功率 ≥ 99% |

### 2.2 核心指标(北极星)
- **次日/7日复用率**(是否真的有用的唯一证据)。
- 单用户知识点掌握度随练习次数的**上升曲线**(证明闭环有效)。

### 2.3 工程指标(简历用)
- LLM 调用层:P99 延迟、失败率、熔断触发次数、队列积压峰值。
- 压测报告:裸系统 vs 加装甲后的成功率 / P99 对比数据。

## 3. 用户与场景

### 3.1 目标用户
- 主:准备秋招的计算机专业学生(后端/AI 方向),与作者同届同圈层。
- 次:已工作想跳槽、需刷八股的后端工程师。

### 3.2 核心场景
1. **按岗位复习**:上传简历 + 选目标岗位 → 系统出题 → 答 → 评分 → 看薄弱点 → 继续。
2. **错题重练**(P1):输入自己做错的题 → 定位知识点 → 生成同知识点相似题。
3. **模拟面试**(P1):AI 扮演面试官多轮追问,结束后出复盘报告。

---

## 4. 核心闭环(产品灵魂)

```
上传简历 / 选岗位
   → AI 按简历+岗位+薄弱点出题
   → 用户答题
   → AI 评分 + 把错处定位到"具体知识点"(结构化输出)
   → 更新用户"知识点掌握度画像"
   → 下一轮按薄弱点 + 遗忘曲线加权出题
   → 循环
```

**MVP 只做这一圈的最小版本**:
> 上传简历 → 出 1 道题 → 答 → AI 评分并定位知识点 → 存库 → 下次出题时"答错过的知识点概率翻倍"。

无需登录、无需华丽界面、LLM 调用可先同步阻塞。先证明内核成立。

## 5. 功能需求(按优先级)

### 5.1 P0 — MVP 裸闭环
| 编号 | 功能 | 说明 |
|---|---|---|
| F-01 | 简历上传与**高精度解析** | 上传 PDF/Word→抽纯文本→**喂 LLM 结构化输出** `{技能清单,项目经历,工作年限,匹配岗位,技能熟练度推断}`。走 LLM 而非正则规则=格式鲁棒性拉满,即"最高精度"的落地实现。图片/扫描件 OCR 列 P1 |
| F-02 | 岗位选择 | 预置若干岗位标签(Java后端/Go后端/AI应用等) |
| F-03 | AI 出题 | 按简历技能 + 岗位 + 薄弱点,生成一道题(含参考答案与所属知识点) |
| F-04 | 答题提交 | 用户文本作答 |
| F-05 | AI 评分 + 知识点定位 | LLM 结构化返回 `{得分, 知识点, 掌握度判定, 漏洞描述, 改进建议}` |
| F-06 | 知识点掌握度画像 | 存储每个知识点的掌握度、最近练习时间、正确率 |
| F-07 | 加权出题 | 下一题按"掌握度低 + 久未练"加权抽取知识点 |

### 5.2 P1 — 闭环增强
| 编号 | 功能 | 说明 |
|---|---|---|
| F-08 | 多轮追问 | AI 面试官基于上一答继续追问,形成对话 |
| F-09 | 间隔重复算法 | 引入 SM-2 / 遗忘曲线,计算每个知识点"下次应复习时间" |
| F-10 | 错题输入 | 用户贴错题 → 定位知识点 → 生成相似题 |
| F-11 | 复盘报告 | 一次面试/一轮练习后,生成弱点总结与建议 |
| F-12 | 画像可视化 | 知识点掌握度雷达图/热力图 |
| F-13 | 用户系统 | 注册/登录,支持部署给他人用 |

### 5.3 P1/P2 — 工程装甲(简历核心亮点)
| 编号 | 功能 | 说明 |
|---|---|---|
| F-14 | LLM 异步队列 | 请求入队削峰,worker 按速率消费 |
| F-15 | 令牌桶限流 | 贴合 LLM 配额,主动保护,防雪崩 |
| F-16 | 多级缓存 | 相似题/知识点结果缓存,降本 |
| F-17 | 超时/重试/熔断/降级 | LLM 抽风时用户看到"稍等"而非 500 |
| F-18 | 流式输出(SSE) | 面试官逐字输出,体验掩盖 LLM 慢 |
| F-19 | 可观测性 | 日志 + 指标(QPS/P99/失败率/队列积压)+ 压测报告 |

### 5.4 P2 — 商业化模块(额度/计费)
| 编号 | 功能 | 说明 |
|---|---|---|
| F-20 | BYOK(自带 Key) | 用户填自己的 API Key,**加密存储**,成本转嫁,作者零成本 |
| F-21 | 额度计费系统 | 按 token 计量 → 原子扣减余额 → 流水记录 |
| F-22 | 充值(两档可插拔) | **默认档**:后台人工生成兑换码发给付款者。**进阶档**:支付宝**沙箱**全自动"下单→回调验签→发码",代码与真实接入一致但不碰真钱/资质 |
| F-23 | 对账与一致性 | 调用成功/扣费失败的补偿,最终一致性 |

> F-20~F-23 的技术含量:原子扣减(Redis+Lua)、密钥加密(KMS/对称加密)、幂等、对账、补偿事务——真实业务逼出的并发与一致性亮点。

## 6. 关键设计:掌握度画像与加权出题

### 6.1 数据模型(核心)
- **知识点(KnowledgePoint)**:id、名称、所属领域(如 Redis/JVM/MySQL)、标签。
- **用户画像(UserKnowledgeState)**:userId、kpId、掌握度分(0~100)、练习次数、正确次数、最近练习时间、下次应复习时间(SM-2 计算)。
- **题目(Question)**:id、题干、参考答案、所属知识点、难度、来源(AI生成/错题衍生)。
- **答题记录(Answer)**:id、userId、questionId、用户答案、得分、LLM评语、定位到的知识点漏洞、时间。

### 6.2 加权出题逻辑(MVP 简化版)
- 每个知识点权重 = f(掌握度越低权重越高, 越久没练权重越高)。
- MVP 可极简:**答错过的知识点,被抽中概率 ×2**。
- P1 升级为 SM-2:按 `下次应复习时间` 到期的知识点优先出题。

## 7. 商业模式(明确边界)

- **BYOK**:用户自带 API Key,作者零成本 → 保住"敢让人用"这条命。
- **卖额度**:用户充值额度用作者的 Key,作者赚差价。
- **边界**:**计费系统做全部技术**(计量/原子扣减/流水/对账/密钥加密)。充值分两档:
  - **默认档**:人工兑换码——用户付款(支付宝转账)→ 作者看账单手动生成码 → 用户兑换额度。零技术成本,解耦"支付"与"额度",规避直接卖 API 的灰色地带。
  - **进阶档**:支付宝**沙箱**——完整实现"下单→异步回调验签→订单状态机→自动发码→对账",用沙箱环境不碰真钱、不需商户资质,面试可讲"支付回调与对账全流程"。
- **为何不接个人真实收款**:个人无商户号,拿不到支付宝订单查询/通知 API,无法编程自动对账;真实接入需营业执照/个体户资质,且回调/退款/对账是时间黑洞。沙箱已能展示全部技术,真金收款列远期可选。
- 面试话术:"计费与额度系统完整实现(原子扣减/流水/对账/密钥加密);支付用支付宝沙箱跑通回调与对账全流程,真实收款涉及商户资质,非本项目验证重点。"

## 8. 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 + BFF | TS / Next.js + React | 满足"学 TS";AI 流式对话体验天然在前端 |
| 核心后端 | **Java / SpringBoot(单体)** | 作者最熟、秋招后端岗基数最大;不上 SpringCloud(少考,深度>广度) |
| 缓存/队列 | Redis(单机) | 画像缓存、出题队列、限流、原子扣费 |
| 存储 | MySQL(单机) | 画像、题库、流水 |
| AI 编排 | Java 侧调 LLM API | Day 1 先接**一家**跑通;P1 抽象成**多 provider 适配器**(OpenAI/Claude/国产通用) |
| 容错 | Resilience4j | 限流/熔断/重试 |
| 监控 | Micrometer + Prometheus/Grafana | 可观测性与压测指标 |
| 压测 | JMeter / wrk | 自己打自己,出瓶颈数据 |

> 形态:**网页**(能发链接给同学 = "真有人用" 的前提),不做客户端。

## 9. 高并发与"固若金汤"策略

**定位(必须诚实表述)**:真实并发只有几十,**主动按几千并发标准设计与压测**,练工程能力 + 留余量。

真正第一个崩的是 **LLM API 层**(慢、贵、有硬限流),不是 DB/服务。因此策略集中在 LLM 调用层:

- 异步 + 队列(削峰)
- 令牌桶限流(保护配额)
- 多级缓存(降本降压)
- 超时/重试/熔断/降级(不雪崩)
- 流式输出(体验掩盖延迟)

"固若金汤" = **扛得住(性能)+ 不怕错(容错)+ 看得见(可观测)**,三者缺一不可,其中后两者是差异化加分点。

**顺序铁律**:先让裸闭环能跑(Day 1)→ 再逐层焊装甲并压测验证(Day 2)→ 再加计费(Day 3)。顺序颠倒必烂尾。

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| 范围膨胀导致烂尾 | 严守 P0 优先,Day 1 只做裸闭环 |
| LLM 评分不稳定/乱编 | 结构化输出 + RAG 喂权威资料 + 规则兜底 |
| token 成本烧穿 | BYOK + 缓存 + 限流 |
| "高并发"表述穿帮 | 诚实表述"低真实并发,高标准设计",用压测数据说话 |
| 支付合规风险 | 默认人工兑换码 + 进阶支付宝沙箱,不接个人真实收款(无商户号/需资质/时间黑洞) |
| 没有真实用户 | 先瞄准同届同学,降低冷启动门槛 |

## 12. 决策记录(已拍板)

1. ✅ 目标岗位:**后端 + AI 应用**一个大类,不细分。
2. ✅ MVP 形态:**直接做可部署网页**(代价:内核验证比"先本地"慢几天,接受)。
3. ✅ LLM:**Day 1 接一家跑通,P1 抽象成多 provider 适配器**(通用多家)。
4. ✅ 知识点体系:**LLM 自己生成知识点树 + 人工轻度校准**。
5. ✅ 简历解析:**MVP 追求最高精度**,实现路径 = 文本抽取 + LLM 结构化解析(非正则);图片/OCR 列 P1。
6. ✅ 支付:**两档可插拔**——默认人工兑换码,进阶支付宝沙箱;真实收款远期可选。
7. ✅ 架构:**单体 SpringBoot + 单机 Redis/MySQL**,不上 SpringCloud、不上集群。
