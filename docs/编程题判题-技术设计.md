## 2. 总体流程

### 2.1 编程题详情

```
GET /api/questions/{id}/coding
  → 校验题目存在且 judge_mode = CODING
  → 查 is_sample=1 的用例（按 sort 排序）下发
  → 隐藏用例不出库
  → 统计当前用户提交次数、是否有 ACCEPTED
  → 返回题面、starter_code、时限/内存、例题、进度状态
```

### 2.2 运行样例（同步）

```
POST /api/questions/{id}/run  { language, code }
  → 校验语言（JAVA / PYTHON）、代码非空、长度 ≤ 64KB
  → 取例题；为空直接 400
  → 用户级并发锁：同一用户同时只允许一个运行/判题任务
  → JudgeService.judge(...) 逐用例跑容器
  → 返回 CodeRunResult（状态、通过数、耗时、逐用例对比）
  → 不写提交历史
```

### 2.3 提交判题（异步）

```
POST /api/questions/{id}/submissions  { language, code }
  → 取全部用例（例题 + 隐藏用例）
  → 占用用户级并发锁
  → 插入 question_submissions，status = PENDING，total = 用例数
  → 投递单线程执行器，立即返回 PENDING 记录
  ↓ 判题线程
  → 更新 status = RUNNING
  → JudgeService.judge(...)
  → 更新 status / passed / total / runtime_ms / error_message / finished_at
  → questionBankService.recordCodingOutcome(...)（best-effort）
  → finally 释放用户级并发锁

GET /api/questions/submissions/{submissionId}
  → 校验归属，返回最新状态
```

前端收到 PENDING 后每 1.2s 轮询一次，进入终态后刷新提交历史与题目状态。

### 2.4 结果联动

```java
recordCodingOutcome(userId, questionId, accepted, code, message)
  → 通过：score = 5；未通过：score = 1
  → upsertProgress：attempt_count + 1，更新 best_score / last_score / status
```

## 3. 判题沙箱

### 3.1 容器参数

每个用例（以及 Java 的编译阶段）都启动一个一次性容器：

```bash
docker run --rm \
  --name grindset-judge-<random> \
  --network none \
  --cpus 0.5 -m 256m --pids-limit 64 \
  --cap-drop ALL --security-opt no-new-privileges \
  --read-only --tmpfs /tmp:rw,size=64m \
  -v <临时目录>:/workspace -w /workspace \
  <镜像> sh /workspace/runner.sh <秒数> <程序命令...>
```

| 参数 | 目的 |
|---|---|
| `--network none` | 禁止访问网络，防外连与拉取数据 |
| `--cpus 0.5` / `-m 256m` | 限制算力与内存，避免拖垮宿主机 |
| `--pids-limit 64` | 防 fork 炸弹 |
| `--cap-drop ALL` + `no-new-privileges` | 去掉内核能力，禁止提权 |
| `--read-only` + `/tmp` tmpfs | 根文件系统只读，仅工作目录与 /tmp 可写 |
| `--rm` | 用完即删，不留容器 |

### 3.2 执行协议

- 用户代码从**标准输入**读、向**标准输出**写，不依赖函数签名，语言间行为一致；
- Java：工作目录写 `Main.java`，先 `javac -encoding UTF-8 -d out Main.java`，再逐用例 `java -cp out Main`；
- Python：写 `main.py`，逐用例 `python3 -I -B main.py`（`-I` 隔离环境变量与用户目录，`-B` 不写 pycache）；
- 输入不在命令行拼接，而是每个用例写 `input.txt`，由容器内脚本重定向，避免 Windows 下参数转义问题；
- 超时用容器内 `timeout <秒>` 控制，超时退出码 124；宿主机侧再有 `时限 + 15s` 的兜底，超时后按容器名 `docker rm -f` 强杀。

容器内运行脚本（`runner.sh`）：

```sh
limit=$1
shift
s=$(date +%s%N)
timeout "$limit" "$@" < /workspace/input.txt
rc=$?
e=$(date +%s%N)
echo "__ELAPSED__$(( (e - s) / 1000000 ))" >&2
exit $rc
```

`__ELAPSED__` 是程序自身耗时（不含容器启动），由 Java 侧解析后回填 `runtime_ms`。

### 3.3 结果判定

| 情况 | 状态 |
|---|---|
| javac 非 0 退出 | `COMPILE_ERROR`，展示 javac stderr |
| 容器内 `timeout` 触发（退出码 124） | `TIME_LIMIT_EXCEEDED` |
| 程序非 0 退出 | `RUNTIME_ERROR`，展示 stderr 摘要 |
| 输出与期望不一致 | `WRONG_ANSWER`，记录首个失败用例 |
| 全部用例一致 | `ACCEPTED` |
| Docker 不可用 / 镜像缺失 / 执行异常 | `SYSTEM_ERROR`，提示缺哪个镜像 |

输出比对前做归一化：统一 `\r\n`，去掉每行行尾空白与末尾空行，其余字符严格相等。单次输出与错误信息分别截断到 20KB / 4KB，防止刷屏。

### 3.4 镜像与国内网络

| 语言 | 默认镜像 | 说明 |
|---|---|---|
| Java | `eclipse-temurin:21-jdk-alpine` | 精简 JDK，含 javac，体积明显小于完整版 |
| Python | `python:3.12-slim` | 官方 slim 版 |

镜像可通过配置覆盖，便于走镜像站：

```yaml
app:
  judge:
    java-image: ${JUDGE_JAVA_IMAGE:eclipse-temurin:21-jdk-alpine}
    python-image: ${JUDGE_PYTHON_IMAGE:python:3.12-slim}
```

国内网络实测：直连 Docker Hub 速度只有几百 KB/s；`docker.m.daocloud.io` 可用，`docker.xuanyuan.me` 返回 403。建议先按镜像站全名 pull，再 `docker tag` 成本地标准名：

```bash
docker pull docker.m.daocloud.io/library/eclipse-temurin:21-jdk-alpine
docker tag  docker.m.daocloud.io/library/eclipse-temurin:21-jdk-alpine eclipse-temurin:21-jdk-alpine
```

镜像缺失时判题直接返回 `SYSTEM_ERROR` 并提示需要 pull 的镜像名，不会阻塞在下载上。

## 4. 数据模型

| 字段 | 类型 | 说明 |
|---|---|---|
| `judge_mode` | VARCHAR(8) | `TEXT` 问答（默认）/ `CODING` 编程 |

`type` 枚举新增 `CODE`，用于列表标签展示；判题开关以 `judge_mode` 为准。

### 4.2 question_test_cases

| `id` | BIGINT | 雪花 ID |
| `question_id` | BIGINT | 关联题目 |
| `input` | TEXT | 标准输入 |
| `expected_output` | TEXT | 期望输出 |
| `is_sample` | TINYINT | 1 例题（下发前端）/ 0 隐藏用例 |
| `sort` | INT | 执行顺序 |
| `created_at` | DATETIME | 创建时间 |

索引：`idx_question_sample (question_id, is_sample, sort)`。

### 4.3 question_submissions

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT | 雪花 ID |
| `user_id` / `question_id` | BIGINT | 归属 |
| `language` | VARCHAR(16) | `JAVA` / `PYTHON` |
| `code` | MEDIUMTEXT | 提交代码 |
| `status` | VARCHAR(32) | 见状态机 |
| `passed` / `total` | INT | 通过用例数 / 总数 |
| `runtime_ms` | INT | 全部用例累计耗时 |
| `error_message` | TEXT | 编译/运行错误或首个失败用例说明 |
| `created_at` / `finished_at` | DATETIME | 提交与判题结束时间 |

索引：`idx_user_question_created (user_id, question_id, created_at)`、`idx_question_created (question_id, created_at)`。

## 5. 接口设计

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/questions/{id}/coding` | 编程题详情（题面 + 例题 + 初始代码 + 进度） |
| POST | `/api/questions/{id}/run` | 运行例题，同步返回逐用例对比 |
| POST | `/api/questions/{id}/submissions` | 提交代码，返回 PENDING 记录 |
| GET | `/api/questions/submissions/{submissionId}` | 查询判题结果（轮询） |
| GET | `/api/questions/{id}/submissions` | 我的提交历史（最近 20 条） |

请求体统一为：

```json
{ "language": "JAVA", "code": "..." }
```

`run` 响应示例：

```json
{
  "status": "ACCEPTED",
  "passed": 2,
  "total": 2,
  "runtimeMs": 40,
  "errorMessage": null,
  "cases": [
    { "index": 1, "input": "4 9\n2 7 11 15", "expectedOutput": "0 1",
      "actualOutput": "0 1\n", "passed": true, "message": "通过" }
  ]
}
```

提交记录对隐藏用例只回传 `passed / total`，不回传输入与期望输出。所有接口走 JWT 鉴权，提交记录校验归属。

## 6. 前端设计

### 6.1 页面结构

`QuestionDetailPage` 拿到详情后，`judgeMode === 'CODING'` 直接渲染 `CodingWorkspace`，其余仍走原来的问答题界面。

`CodingWorkspace` 左右分栏：

- 左栏：题面、例题（输入/期望输出）、提交历史（最近 20 次，状态 + 通过数 + 时间）；
- 右栏：语言切换（Java / Python）、Monaco 编辑器、运行样例 / 提交按钮、结果面板。

结果面板优先级：本次运行结果 > 最近一次提交 > 操作提示。提交后展示“排队中 / 判题中”，进入终态后自动刷新历史与题目状态。

### 6.2 Monaco 接入

- 依赖 `@monaco-editor/react` + `monaco-editor`；
- 使用本地打包：`loader.config({ monaco })`，并用 `monaco-editor/editor/editor.worker?worker` 提供 worker，不依赖外部 CDN，离线可用；
- 编辑器关闭 minimap、开启自动布局与自动换行，Java/Python 各自保留编辑内容，切换语言不清空。

### 6.3 交互约束

- 运行与提交期间按钮禁用，避免连点；
- 后端同一用户同时只允许一个运行/判题任务，重复请求返回 429；
- 代码为空或超长在前端后端都会拦截（上限 64KB）。

## 7. 状态机与错误处理

提交状态：

```
PENDING → RUNNING → ACCEPTED
                  → WRONG_ANSWER
                  → COMPILE_ERROR
                  → RUNTIME_ERROR
                  → TIME_LIMIT_EXCEEDED
                  → SYSTEM_ERROR
```

| 场景 | 用户看到 |
|---|---|
| 编译失败 | 红色错误块，原文展示 javac 报错 |
| 运行异常 | 用例序号 + stderr 摘要 |
| 超时 | “用例 N 运行超时（限制 2000ms）” |
| 答案错误 | 首个不一致用例序号，例题可看到实际输出 |
| 系统错误 | 缺镜像时直接提示 `docker pull <镜像>` |

异常兜底：判题线程出现未捕获异常时，把该提交置为 `SYSTEM_ERROR` 并写 `error_message`，同时释放并发锁。

## 8. 性能与容量

| 项 | 现状 | 说明 |
|---|---|---|
| 判题并发 | 单线程执行器 | 单机串行，避免多个容器争抢 CPU |
| 用户并发 | 每用户同一时刻 1 个任务 | `activeUsers` 集合，防连点刷爆判题机 |
| 每用例开销 | 一次 `docker run` | 实测 Java 单用例约 95ms，Python 约 20ms（不含容器启动） |
| 运行样例 | 同步 | 只跑例题，通常 2 个，耗时可控 |
| 提交判题 | 异步 + 轮询 | 接口立即返回，避免长请求占线程 |
| 提交历史 | 最近 20 条 | 足够复盘，避免大 payload |

后续可优化点：容器预热池、一个容器跑全部用例摊掉启动开销、判题队列外置（Redis Stream / MQ）、多机判题。

## 9. 安全说明

- 用户代码只在一次性容器内执行，不接触宿主机文件系统（仅挂载临时工作目录）；
- 断网、去能力、禁提权、只读根文件系统、限进程数/内存/CPU；
- 代码长度限制 64KB，输出与错误信息截断，防日志与响应膨胀；
- 隐藏用例不下发，前端无法直接拿到期望输出；
- 提交记录按 `user_id` 校验归属，不能查看他人结果；
- 已知限制：容器内仍以 root 运行，首版未自定义 seccomp/AppArmor；如需面向公网开放，建议补 `--user`、seccomp 配置与独立的判题节点。

## 11. 部署与使用

1. 执行建表：`sql/008_coding_schema.sql`（可重复执行）；
2. 执行种子：`sql/009_coding_seed.sql`（按主键/内容哈希幂等）；
3. 准备镜像：

   ```bash
   docker pull python:3.12-slim
   docker pull docker.m.daocloud.io/library/eclipse-temurin:21-jdk-alpine
   docker tag  docker.m.daocloud.io/library/eclipse-temurin:21-jdk-alpine eclipse-temurin:21-jdk-alpine
   ```

5. 启动后端与前端，登录后进入 `/questions`，选择类型为“编程”的题目即可。

新增编程题时需要写：题目（`judge_mode='CODING'`、`starter_code`、时限/内存）、至少 1 条例题、若干隐藏用例；隐藏用例的输入输出只存库，不会下发前端。

## 12. 已知限制

- 只支持 Java / Python，新增语言需补镜像、启动命令与前端选项；
- 每个用例单独起容器，判题整体耗时随用例数线性增加；
- 单机串行判题，多用户同时提交会排队；
- 未做代码查重、抄袭检测与运行日志留存（只存代码与结果）；
- 未支持自定义输入运行、函数式判题（当前统一为标准输入/输出模型）。
