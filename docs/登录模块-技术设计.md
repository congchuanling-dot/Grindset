## 1. 范围

| 登录方式 | provider | MVP 做不做 | 说明 |
|---|---|---|---|
| 账号 + 密码 | `LOCAL` | ✅ 做 | 账号、密码随意填(不校验邮箱格式/密码强度),但密码必须 BCrypt 哈希存储 |
| GitHub 一键 | `GITHUB` | ⏸ 预留 | 结构已留位,因需申请 OAuth App 凭证,暂不实现 |
| Google 一键 | `GOOGLE` | ⏸ 预留 | 同上,需 Google Cloud OAuth client |
| 邮箱验证码 | `EMAIL_CODE` | ⏸ 预留 | 发信通道(阿里云/腾讯云)以后再接,留 `EmailSender` 接口 |

**账号合并策略**:不同登录方式产生的账号**各算各的,MVP 不合并**(没有验证过的邮箱无法可靠合并,强行合并有安全坑)。合并列 P1。

## 2. 数据模型

拆两张表:`users` 记"人",`user_identities` 记"这个人的某种登录方式"。一个人可挂多条身份。

### 2.1 users

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | 主键,答题记录等业务表外键指它 |
| nickname | VARCHAR | 展示名 |
| avatar_url | VARCHAR NULL | OAuth 头像,可空 |
| email | VARCHAR NULL | 仅展示/未来合并用,**不验证、不唯一** |
| status | TINYINT | 0 正常 / 1 禁用 |
| created_at | DATETIME | |
| updated_at | DATETIME | |

### 2.2 user_identities

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | |
| user_id | BIGINT FK | 指向 users.id |
| provider | VARCHAR | `LOCAL` / `GITHUB` / `GOOGLE` / `EMAIL_CODE` |
| identifier | VARCHAR | LOCAL=账号名;OAuth=对方唯一 id(sub) |
| credential | VARCHAR NULL | **仅 LOCAL 有值**=BCrypt 哈希;OAuth 为空 |
| created_at | DATETIME | |

**唯一约束**:`UNIQUE(provider, identifier)` —— 同一种登录方式下标识不可重复(账号名不重复 / 同一 GitHub 账号不重复绑)。

**加新登录方式 = 加一行记录,不改表结构**,这是拆两张表的核心收益。

## 3. 认证与会话:双 Token

| Token | 形态 | 有效期 | 存哪 | 作用 |
|---|---|---|---|---|
| access token | JWT(无状态) | 30 分钟(可配) | 前端内存 / sessionStorage | 每次请求验签,不查库 |
| refresh token | 32 字节随机串(不可预测) | 7 天(可配) | 后端 Redis + 前端 **HttpOnly Cookie** | 换新 access token |

### 3.1 access token

- 载荷含 `userId`(subject)、`typ=access`、签发/过期时间;HMAC-SHA 签名,密钥至少 32 字节。
- 拦截器只验签 + 查过期 + 校验 `typ`,**不查数据库**,保证高频请求轻量。
- 允许 60s 时钟偏移;签名密钥放环境变量 `JWT_SECRET`。

### 3.2 refresh token

- 随机串,Redis 只存 **SHA-256 摘要**,不落明文:`auth:refresh:{sha256(token)} → userId`,TTL = refresh 有效期。
- 下发时写进 **HttpOnly + SameSite + Secure(可配)** Cookie,`Path=/api/auth`,JS 读不到,防 XSS 窃取。
- 刷新时**轮换**:用 `GETDEL` 原子消费旧 token,再签发新的一对;重复使用旧 token 直接 401。
- 登出 = 删除对应 Redis key + 清 Cookie,即时失效。
- 现状限制:没有 token family,同一账号的多设备会话互相独立;「登出所有设备」「被盗 token 复用检测」列 P1。

## 4. 接口设计

统一前缀 `/api/auth`,成功响应下发 access token(响应体)+ refresh token(Set-Cookie)。

### 4.1 MVP 实现

| 方法 | 路径 | 入参 | 行为 |
|---|---|---|---|
| POST | `/register` | `{account, password}` | 入参校验 → IP 限流(10 次/小时)→ `(LOCAL, account)` 不存在则建 user + LOCAL 身份(BCrypt 存 password);已存在 → 409 |
| POST | `/login` | `{account, password}` | 账号/IP 限流检查 → 查 `(LOCAL, account)` → BCrypt 校验;失败统一 401,成功签发双 token;超限 429 |
| POST | `/refresh` | (Cookie 带 refresh) | `GETDEL` 原子消费旧 refresh,轮换并下发新双 token;失效则清 Cookie + 401 |
| POST | `/logout` | (Cookie 带 refresh) | 删 Redis key,清 Cookie |
| GET | `/me`(`/api/auth/me`) | (Header 带 access) | 返回当前用户信息,前端判登录态 |

**错误约定**:

- 登录失败统一返回"账号或密码错误",不区分"账号不存在/密码错",避免账号枚举。
- 触发限流返回 **429**,文案中性(「尝试过于频繁，请 1 分钟后再试」),不暴露账号状态。
- 资源归属校验失败统一 404(与项目其它模块一致)。

### 4.2 预留(暂不实现)

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/github` → `/github/callback` | 换 code → 拉用户 → 按 `(GITHUB, sub)` 查/建身份 → 签发本系统 token |
| GET | `/google` → `/google/callback` | 同上,provider=GOOGLE |
| POST | `/email/code`、`/email/verify` | 验证码发送/校验,依赖 `EmailSender` |

OAuth 回调关键原则:**换成本系统自己的 token,绝不把第三方 token 下发给前端。**

## 5. 前端设计(Vite + React)

> 注:仓库实际前端为 **Vite + React 19 + TS**(非 PRD 最初设想的 Next.js)。Vite 是纯前端 SPA、无服务端中间层,相关设计已按此调整:路由守卫改用 React Router,HttpOnly Cookie 由 Java 后端直接下发。

- **`/login` 路由**:账号 + 密码两个输入框 + 登录/注册切换;下方预留"用 GitHub / Google 登录"按钮(MVP 可灰置或隐藏)。
- **路由守卫(React Router)**:用一个受保护路由包裹组件,未登录则重定向 `/login`(替代 Next.js 的 `middleware.ts`)。
- **fetch 包装器**:自动带 `Authorization: Bearer <access>`;遇 401 → 自动调一次 `/refresh`(浏览器自动带 HttpOnly Cookie)→ 成功则重试原请求,失败才跳 `/login`。
- **access token 存内存**:刷新页面内存丢失后,首次请求 401 → 走 refresh 自动恢复登录态。
- **Cookie 下发方**:纯 SPA 无 BFF,refresh token 的 HttpOnly Cookie 由 **Java 后端**直接 `Set-Cookie`;前后端分离需配好 **CORS**(允许携带凭证)与 Cookie 的 `SameSite` / 域设置。

## 6. 安全要点

- 密码一律 **BCrypt(强度 10)加盐哈希**,绝不存明文;实测单次校验约 75~100ms CPU,这也是限流存在的意义。
- refresh token 走 **HttpOnly Cookie**,access token 不落 localStorage,降低 XSS 风险。
- JWT 密钥、(未来的)OAuth client secret 全部走**环境变量**。
- 登录错误信息不泄露账号是否存在。
- 登录/注册接口做限流,防撞库与批量建号(见 6.1、6.2)。

### 6.1 登录失败限流(已实现)

**动机**:BCrypt 每次约 100ms CPU,撞库/爆破会被放大成 CPU 打满。限流检查必须放在 BCrypt **之前**,超限的请求 6~7ms 就返回,不进哈希计算。

**算法:双桶加权(近似滑动窗口)**

```
T          = 桶时长(窗口的一半)
cur        = floor(now / T)          // 当前桶编号
elapsed    = now % T                 // 本桶已过去的时间
prevWeight = (T - elapsed) / T       // 上一桶按「剩余比例」衰减
estimate   = floor(prevCount * prevWeight) + curCount
```

刚切桶时上一桶权重为 1,桶末尾趋近 0,因此固定窗口在边界处的「两倍突刺」被抹平。`estimate >= 阈值` 即拒绝。

**规则**

| 维度 | 阈值 | 窗口 | 桶长 T | 说明 |
|---|---|---|---|---|
| 账号 | 5 次 | 60s | 30s | 只统计密码错误;账号不存在同样计数 |
| 来源 IP | 30 次 | 60s | 30s | 只统计密码错误,防止换账号打同一出口 |

**Redis Key**

```
auth:rl:login:acct:{sha256(trim+lowercase(account))}:{bucket}
auth:rl:login:ip:{ip}:{bucket}
```

- 账号做 SHA-256,Redis 不落明文邮箱;`lowercase` 与库表 `utf8mb4_0900_ai_ci` 的大小写不敏感匹配保持一致,否则可用大小写变体绕过计数。
- 桶 key 的 TTL = `2T + 60s`,保证上一桶在被读取期间不过期。
- 只在首次 `INCR` 时设置 TTL,避免每次续命。

**Lua 脚本**(位于 `backend/src/main/resources/lua/`,Java 侧用 `RedisScript.of(ClassPathResource)` 加载)

- `login_rate_limit_estimate.lua`:读取上一桶/当前桶,按公式返回估算值,只读。
- `login_rate_limit_record.lua`:失败时 `INCR` 当前桶,首次写入设置 TTL。

实现位置:`service/auth/LoginRateLimiter`(阈值/桶长暂为常量,后续可挪到配置项);IP 提取在 `common/ClientIp`(X-Forwarded-For 首段 → X-Real-IP → `getRemoteAddr()`)。

**执行顺序**

```
validateCredentials(纯内存)
→ check(account, ip)          // Redis 只读估算,超限 429
→ findLocal(account)          // 1 次 DB 查询
→ BCrypt.matches(...)         // 唯一 100ms 的 CPU 消耗点
   ├─ 失败/账号不存在 → recordFailure(account, ip) → 401
   └─ 成功 → 签发 token(成功不计数)
```

**语义**

- 只计失败:5 次/分钟错误容忍度,正常用户几乎无感。
- 成功不重置计数,让失败自然衰减;避免「撞对一次就清零」被利用。
- 账号不存在与密码错误走同一分支、同一文案、同一计数。

**降级**:Redis 异常(fail-open)只记 WARN 并放行,不能让限流组件成为登录单点故障。为此在 `application.yml` 收紧超时:

```yaml
spring:
  data:
    redis:
      connect-timeout: 500ms
      timeout: 1s
```

否则 Redis 故障时 Lettuce 默认超时会把登录挂住十几秒,降级形同虚设(实测降级耗时从 >15s 降到约 2.2s)。

**已实测**(登录接口,真实 HTTP 调用)

| 场景 | 结果 |
|---|---|
| 前 5 次错误密码 | 401 ×5,计数 1→5 |
| 第 6、7 次 | 429,计数冻结在 5,约 6~7ms 返回 |
| 跨桶边界后 | `floor(5 × 28/30) = 4 < 5`,放行;上一桶 key 保留 |
| 成功登录 | 200,不新增计数 |
| IP 维度 | 7 个账号共 35 次失败,第 31 次起 429 |

### 6.2 注册限流(已实现)

**规则**:来源 IP **10 次/小时**,窗口 3600s,桶长 1800s,双桶加权同上。

- Key:`auth:rl:register:ip:{ip}:{bucket}`,TTL = `2×1800 + 60s`。
- 脚本 `register_rate_limit_check.lua`,实现位置 `service/auth/RegisterRateLimiter`。
- 与登录不同,**统计的是尝试次数而不是失败次数**——攻击目标是批量建号,成功注册同样消耗额度。
- 检查与累加在同一个 Lua 里原子完成(`register_rate_limit_check.lua`):估算未超限才 `INCR`,返回 `-1` 表示超限,没有 check-then-act 的超发窗口。
- 入参校验失败(400)不计数;重复邮箱(409)计数,顺带堵住用状态码差异批量探测邮箱的路径。
- Redis 异常同样降级放行。

### 6.3 事务与资源边界

- **注册**:`validateCredentials`、限流 Redis 调用、`BCrypt.encode` 全部在事务外;`TransactionTemplate` 只包两次 insert。避免 ~100ms 的 CPU 计算占着 Hikari 连接,并发注册时打满连接池。重复账号在 encode 之前快速失败,不白烧一次哈希。
- **登录**:无事务;先限流后 BCrypt;`identity == null` 短路的时序差异是已知缺口(建议补 dummy hash 拉平,见 6.4)。
- **Redis 超时**:见 6.1,默认收紧到 500ms 连接 / 1s 命令。

### 6.4 已知缺口(P1/P2)

- 登录时「账号不存在」直接短路,响应时间(约 1ms)明显短于密码错误(约 80ms),理论上可用于时序枚举;可对固定 dummy hash 跑一次 `matches` 拉平。
- `requireActiveUser` 在签发 token 之后才执行,禁用账号登录会先在 Redis 留下一个孤儿 refresh token(7 天 TTL);应把状态校验前移。
- 429 未返回 `Retry-After`,前端无法做精确倒计时。
- `/api/auth/refresh` 未限流,可用随机 token 刷 `GETDEL`。
- access token 30 分钟窗口内,禁用用户的存量 token 仍可访问其它接口(`JwtAuthFilter` 不查库)。
- `X-Forwarded-For` 无条件信任,直接暴露公网时可伪造头绕过 IP 维度;部署在可信网关后才应启用,或增加内网来源判断。
- 无登录审计/指标(失败数、429 数、fail-open 次数),建议接 Micrometer 或结构化日志。
